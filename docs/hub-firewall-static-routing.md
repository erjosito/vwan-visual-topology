# Single-hub static Firewall inspection and bypass

Both native VWAN providers (`vwan` and `full`) can assess a bounded single-hub
design with an explicitly declared original local Azure Firewall, CIDR static
routes in Default/custom hub tables, and **both routing intents disabled**.
Existing association, propagation and label rules still apply. The diagram and
tables describe modeled routing, not Firewall-policy permission, established
sessions, guest readiness or application delivery.

## Native authoring and API

On the existing hub object, declare the Firewall and use its exact original ID
as the static next hop. The same fields work on `hubs[]` in native v1 and
`vwanHubs[]` in native v2; this fragment is not a complete topology:

```json
{
  "id": "hub-local",
  "firewall": { "id": "fw-local", "name": "Original local Firewall" },
  "routingIntent": { "private": false, "internet": false, "privatePrefixes": [] },
  "routeTables": [{
    "id": "defaultRouteTable",
    "name": "Default",
    "labels": ["default"],
    "staticRoutes": [{
      "name": "inspect-private",
      "destinationType": "CIDR",
      "destinations": ["10.0.0.0/8"],
      "nextHopType": "ResourceId",
      "nextHop": "fw-local"
    }]
  }]
}
```

In the hub configuration dialog, use **Static hub Firewall routing** to declare
the identity and edit routes. Changing an identity does not silently retarget
old routes: select the new target explicitly. Native JSON import/export and
save/reload retain the original identities, tables and routes. The hub's
effective-route inspector exposes static selection and a separate Firewall
onward-route view.

For an existing `kind: "flow"` requirement with `expectation: "allow"`, add:

```json
"firewallPolicy": {
  "hubId": "hub-local",
  "forward": "required",
  "reverse": "bypassed"
}
```

Both values must be `required` or `bypassed`. Do not combine this field with
legacy `requiredFirewallHubId` or `requiredApplianceId`. Each direction is traced
independently; a forward-only route does not satisfy an allow requirement.
A missing/unknown Firewall identity cannot satisfy even a bypass predicate.
The MCP tools `get_capabilities` and `get_schema` describe this contract;
`start_simulation`, `get_job` and bounded `get_evidence` expose the same native
simulation/assessment evidence as the local API and browser worker. An already
running older MCP process needs the new built source and a restart.

## Selection and evidence

Longest prefix wins. For equal prefixes, a supported static Firewall route
precedes learned/connected alternatives. After inspection, the engine performs
a **different onward lookup** against original local connected/imported routes,
including routes whose hub-table propagation was suppressed. It does not reuse
the ingress static aggregate or invent a second inspection loop. Missing onward
routes are explicit. Native v1 assesses its enumerated paths; native v2 leaves
ambiguous distinct Firewall onward ECMP choices unassessed rather than choosing
a favorable traffic hash. This is not exhaustive arbitrary ECMP qualification.

Unknown resource/IP next hops, noncanonical prefixes, multiple hubs, static
branch-to-branch inspection, and static/custom inspection combined with routing
intent remain unassessed. Ordinary learned branch-to-branch bypass can still be
assessed. Arbitrary NVAs, inter-hub inspection and live Firewall rules/NAT are
not implemented by this contract. Bicep export is not a deployment-equivalence
certificate for the retained static Firewall design.

## Published example and qualification

The document-derived fixtures in `tests/fixtures/hub-firewall.ts` deliberately
separate three contracts:

| Fixture | What it demonstrates |
| --- | --- |
| `published-vnet` | Trusted/trusted bypass; VNet/untrusted and VNet/branch inspection. Static branch inspection is unassessed. |
| `published-branch` | Trusted and branch more-specifics propagate to Default. An untrusted VNet also associated with Default therefore bypasses to trusted, while the reply inspects. |
| `separate-untrusted` | A distinct untrusted association table restores the intended model matrix: trusted/branch bypass, untrusted/branch inspection and trusted/untrusted inspection in both directions. |

Removing branch propagation from Default alone does not remove trusted
more-specifics visible to untrusted sources. Destination-only lookup cannot
distinguish two sources using the same table. The separate-table variant is a
**simulator candidate, not a live-Azure-qualified recommendation**.

The expectations are hand-authored rather than generated by the engine under
test. Passing these tests is document-derived model-contract evidence, not an
Azure semantic-fidelity percentage or a live deployment result.
